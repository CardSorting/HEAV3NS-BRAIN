# SINGULARITY Phase III — current execution record

Status: **in progress; no V4.1 inference or deployment has been demonstrated**. The Phase II documents describe the earlier generic host transformer and do not establish Phase III capabilities.

## Checkpoint evidence

On 2026-10-30 the Hugging Face model API returned revision `1bae0e1088993b9b82de08f59de5be5a34e42170` for `deepseek-ai/DeepSeek-V4.1-Flash-1017`. The configuration fixture at `singularity-model/tests/fixtures/deepseek-v41-flash-1017-config.json` matches the configuration fetched by that immutable revision. Source: https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/tree/1bae0e1088993b9b82de08f59de5be5a34e42170 (MIT license). The index fetched at that revision has 96,085 entries, 48 distinct shard names and `metadata.total_size` 510,286,023,000 bytes. This is an index inspection only; no shard integrity or tensor shapes have been verified.

The config specifies 40 backbone layers, 3 draft layers, four residual streams, Engram layers 1 and 14, and a 32-layer vision encoder. Its quantization metadata specifies FP8, FP4 experts and UE8M0 scales. `v41_config.rs` parses a subset of the config and validates basic topology and quantization fields; it does not implement those operations. DeepInfer's `deepinfer/hugging_face/config.py` was consulted for the layer-source interpretation and quantization checks (Apache-2.0).

`singularity-model/src/engram.rs` implements a CPU reference for tokenizer compression, prime table layout and addressing, including sequence-start and image/dead-token boundaries. Its 1017 multipliers are fixed to the pinned config's 99,092-token compressed vocabulary and layer IDs. The test compares row totals and hash IDs with a separate NumPy/SymPy transcription of the checkpoint's MIT-licensed `inference/engram.py`; the vector generator is `singularity-model/tests/fixtures/engram_reference_vectors.py` (NumPy 2.5.4, SymPy 1.14.0). With the pinned tokenizer, the complete 129,280-entry compression map matched an independently generated Python tokenizers 0.21.4 SHA-256 digest; `engram_compression_reference.py` regenerates it. Run the external-asset test with `SINGULARITY_V41_TOKENIZER=/path/to/tokenizer.json cargo test -p singularity-model checkpoint_compressed_vocabulary_matches_reference -- --ignored`.

`v41_engram.rs` adds CPU row-wise FP8/UE8M0 embedding lookup, quantized projection, and the per-stream normalized residual gate. An entire miniature Engram forward matched a PyTorch CPU formulation. A component test also used four actual layer-14 embedding rows repeated across the 24 hash columns, the real 157,286,400-byte projection, scales and q/k weights, with a synthetic residual. It matched a separate PyTorch CPU formulation with relative RMS error 0.00000005. This is not real-prompt inference, a full checkpoint load, or GPU execution. `Flash1017HashState` now maps raw token IDs incrementally, keeps bounded history and resets per sequence; tests cover image boundaries, failure and reset. Distributed embedding placement and GPU execution remain unimplemented. The bounded shard-48 reference ranges and checksums are available through `scripts/fetch_v41_reference_ranges.py --engram-projection <directory>` (the flag additionally downloads approximately 150 MiB); the ignored full component test requires `SINGULARITY_ENGRAM_ROWS`, `SINGULARITY_ENGRAM_SCALES`, `SINGULARITY_ENGRAM_QK`, `SINGULARITY_ENGRAM_WKV` and `SINGULARITY_ENGRAM_WKV_SCALES`.

`v41_prompt.rs` implements the text-only system/user/assistant protocol in chat and thinking modes, including numeric effort, prior reasoning removal, and mid-conversation system messages. It deliberately rejects unsupported structured messages instead of discarding their fields. Seven vectors were generated with the pinned checkpoint's `encoding/encoding.py` and tokenizer; both serialized text and token IDs were compared. The generator is `singularity-model/tests/fixtures/generate_v41_text_vectors.py` and accepts paths to those pinned files. The token-ID test requires `SINGULARITY_V41_TOKENIZER=/path/to/tokenizer.json cargo test -p singularity-model text_token_ids_match_checkpoint_reference -- --ignored`. Task tokens, images, and serving-path integration are still outstanding.

`v41_tools.rs` adds DSML tool-call serialization and complete assistant-continuation parsing, including namespaces, typed JSON arguments, thinking text and malformed-input rejection. Three vectors were generated with the pinned `encoding/encoding.py` using `generate_v41_tool_vectors.py` and matched both serialization and parsing. The API rejects ambiguous delimiters and invalid JSON rather than attempting recovery. It is not yet connected to serving; task tokens, images, streaming partial parsing and end-to-end tool execution remain outstanding.

`v41_conversation.rs` connects DSML calls to text conversations, merges tool results into user messages, orders results by call ID, and renders checkpoint-format tool schemas with the corresponding reasoning-retention behavior. Four checkpoint-generated prompt vectors cover out-of-order results, merged text, prior reasoning and schema prompts. Its schema API accepts normalized function objects and requires an initial system message; Task tokens, images, streaming parsing and serving integration are still outstanding.

`v41_openai.rs` adapts OpenAI-shaped text, tool-call and function-definition data into the conversation encoder, and maps completed DSML output back to assistant messages with caller-provided unique call IDs. It rejects unsupported structured content and unknown message fields. The adapter is not wired to an inference endpoint and supplies an empty initial system message when tool schemas need one. The host development server now rejects unsupported fields, roles and stop strings rather than silently discarding them; HTTP integration tests cover these rejections. Full V4.1 serving remains outstanding.

`v41_quant.rs` implements CPU reference decoding and matrix-vector operations for E4M3FN dense weights with 32×32 UE8M0 scales and E2M1FN packed experts with per-row, per-32 UE8M0 scales. A borrowed loader view checks dtype, shape and payload sizes without changing checkpoint bytes. The header of pinned shard 9 was retrieved by HTTP byte range: `layers.6.attn.wkv.weight` is `F8_E4M3 [512,5120]` with `F8_E8M0 [16,160]` scales, while `layers.6.ffn.experts.0.w1.weight` is `I8 [2304,2560]` with `F8_E8M0 [2304,160]` scales. Only the header was inspected, not the weight bytes. All 256 FP8 and scale byte values plus synthetic matrix vectors were compared with PyTorch 2.7.1 CPU; the generator is `singularity-model/tests/fixtures/generate_v41_quant_vectors.py`. These matvecs use unquantized FP32 inputs and are not the reference GPU kernel's quantized-activation GEMM; no actual checkpoint output or B200 numerical equivalence has been established.

`v41_hyper.rs` implements CPU Hyper-Connections coefficient projection, Sinkhorn normalization, pre/post transforms and shifted pre-mix state transitions, including optional BF16 activation boundaries. It loads the checkpoint's F32 HC tensors and validates their shapes. Synthetic vectors and two shifted steps were compared against an independent PyTorch CPU formulation. The layer-6 attention HC parameters were also retrieved from pinned shard 9 bytes 261472–2227659 (inclusive; SHA-256 `7c1dbec1f1e4f2e3e70dd6bcfc44304b8dd862a7753f5206fda2f7351cbc09bc`) and compared against PyTorch with a synthetic input. Regenerate vectors with `generate_v41_hyper_vectors.py` and run the real-weight test using `SINGULARITY_V41_HC_ATTN_BYTES=/path/to/range.bin cargo test -p singularity-model checkpoint_hyper_connection_matches_torch_reference -- --ignored`. This is not a full layer test; its input is synthetic, and the component is not yet integrated into a model forward pass or GPU backend.

`v41_sparse.rs` supplies CPU reference primitives for index scoring, candidate-block selection, causal compressed top-k, sliding-window indices and a single-sequence ring, per-coordinate compression pooling, and shared-KV attention with a learned sink. Synthetic attention, index and pooling values were compared against PyTorch CPU; prefill and incremental window results were checked across ring wraparound. Ties use deterministic ascending indices, which may differ from accelerator top-k ties; masked positions remain eligible at negative infinity when fewer than k candidates survive, as in the checkpoint reference. The original ideal-FP32 attention primitive remains available; the model path now uses a separate 64-position online-softmax transcription with BF16 probability rounding. Device cache and GPU execution remain outstanding.

`v41_rope.rs` implements CPU adjacent-pair RoPE and compressed-layer YaRN frequencies selected from checkpoint config; synthetic BF16 vectors at positions up to 1,048,575 were compared to PyTorch. `v41_quant.rs` now also encodes round-to-nearest-even E4M3FN activations with 32-element UE8M0 scales and provides a block-scaled CPU matrix path. The FP8 conversion's representable values and midpoints, plus activation block vectors, were checked against PyTorch. The real expert-309 test now additionally evaluates the quantized-activation path against a separate PyTorch dequantized formulation: observed relative RMS error 0 for that synthetic input. This does not establish TileLang or B200 equivalence; the CPU operations are not yet wired to a full V4.1 attention/model forward pass.

`v41_moe.rs` adds checkpoint-specific sqrt-softplus routing (bias affects selection only), text/image bias handling, routed and shared expert loading, clamped SwiGLU, and single-token local expert aggregation. Its CPU paths include both unquantized and block-quantized activation references; neither is an optimized GPU kernel. Synthetic packed experts and aggregation were compared to PyTorch CPU. The layer-6 BF16 gate weights (shard 9 bytes 4207672–8139831; SHA-256 `6e46b2f91b46aad3420f3dab6dedca03aebf94540f3819dd0c96f29aa5d0dc34`) and text/VL biases (bytes 258400–261471; SHA-256 `0a81d7f8e454f084206ee5db885e3963843ac452873187e4ccf3879055497d42`) were compared with PyTorch for a synthetic input. The selected expert 309 was then loaded from real checkpoint bytes (weights bytes 4735551032–4753245751; scales bytes 267059000–268164919) and evaluated using the gate's route weight. Its 5,120 BF16 outputs matched the corresponding PyTorch CPU calculation in this test (observed relative RMS error 0; tolerance 0.01). Both calculations use synthetic inputs and unquantized activation matvecs. The test constructs a small Safetensors subset and exercises the gate and expert loaders, not the complete distributed checkpoint loader. `scripts/fetch_v41_reference_ranges.py` retrieves these bounded ranges and verifies SHA-256 before storing them; its HTTP rejection paths were tested with mocked responses, while direct Python network access was denied in this environment. The ignored `routed_real_expert_matches_torch_reference` test takes `SINGULARITY_V41_GATE_WEIGHT`, `SINGULARITY_V41_GATE_BIAS`, `SINGULARITY_V41_EXPERT_WEIGHT` and `SINGULARITY_V41_EXPERT_SCALE`. The older generic `MoERouter` has different scoring semantics and is not a V4.1 router. Expert parallelism, GPU execution and full model execution remain unverified.

## Execution boundary

`v41_block.rs` now composes the shifted Hyper-Connections transitions, checkpoint RMS normalization, and the quantized CPU MoE reference for one token. Attention remains a caller-supplied callback, and Engram must be applied separately. A synthetic test checks normalization, sequencing, and rollback of HC state on a sublayer error; callback-owned attention caches are not rolled back. This is not a full block or model correctness validation.

`v41_attention.rs` implements a single-token sliding-window attention reference with query/KV normalization, RoPE, FP8 activation quantization, sink attention and grouped output projection. The uncompressed backbone loader checks and loads checkpoint-format projection, norm and sink tensors, including dequantizing `wo_a` to BF16. Its cache updates only after its output projection succeeds. Synthetic tests cover checkpoint-format loading, ring wraparound and rollback; the path has not been compared end-to-end with actual checkpoint weights. Compressed attention and cross-layer sharing are connected in the CPU reference; GPU execution remains outstanding.

The CPU reference now loads local MoE inventories and connects them to uncompressed attention and HC block execution, rolling back both HC state and window cache when a block fails. A synthetic checkpoint exercises this path and its failure rollback. `v41_io.rs` loads BF16 token embeddings, final norm and head, expands an embedding into HC streams and computes FP32 logits from a collapsed final state. Pinned shard headers confirm `embed.weight` and `head.weight` are BF16 [129280, 5120] and `norm.weight` is BF16 [5120]; only headers were inspected. The IO and block paths have not been validated against full real-model output, and cannot yet execute the compressed backbone.

`v41_compressor.rs` loads BF16 compressor projections and norm and executes single-token compression, including FP32 gated pooling for ratios above one, BF16 boundaries, and reset and error-safe partial state. Pinned shard headers show BF16 compressor weights for layers 2 (ratio 2) and 20 (ratio 1). Synthetic tests exercise both ratios and incomplete-group reset. The compressor alone does not execute attention.

The layer-2 compressor was subsequently tested with actual checkpoint weights from shard 5 bytes 4194808–14681591 (SHA-256 `7d5b93e38f6a67fa63f13f06815b090247cfa13272ae27f5de97fc787e88667d`) and two groups of synthetic inputs. The Rust output matched an independent PyTorch CPU calculation with observed relative RMS error 0 for both groups. The generator is `generate_v41_compressor_real_vectors.py`; fetch the range with `scripts/fetch_v41_reference_ranges.py --compressor <directory>` and set `SINGULARITY_V41_COMPRESSOR` when running the ignored test. This is a component test, not full prompt inference or GPU validation.

`v41_quant.rs` now includes an FP4 activation quantize/dequantize reference for the indexer's 32-element UE8M0 groups and compressed KV's 16-element E4M3 groups. `v41_indexer.rs` loads the checkpoint-format projections and composes key generation, RoPE, FP4 quantization, score and candidate selection for one token; shared keys and masks remain caller-owned. Pinned layer-2 shard headers confirm the relevant tensor dtypes and shapes. Synthetic tests cover quantization ties, loading and causal selection; neither component has been compared with the actual CUDA kernel. The score path now rounds the einsum, multiply and reduction outputs to BF16 as in the checkpoint reference. These primitives alone do not execute compressed attention.

The layer-2 indexer was subsequently tested with real checkpoint projection bytes and synthetic inputs: four generated keys and four scores matched an independent PyTorch CPU formulation with observed relative RMS error 0, and the selected two positions agreed. This uses a reduced top-k for the test and does not establish CUDA or full-model equivalence. The reference ranges can be fetched using `scripts/fetch_v41_reference_ranges.py --indexer <directory>`; the ignored test accepts `SINGULARITY_V41_INDEXER_PROJ`, `SINGULARITY_V41_INDEXER_SCALE`, and `SINGULARITY_V41_INDEXER_QUERY`. The vector generator is `generate_v41_indexer_real_vectors.py`.

`v41_compressed_attention.rs` now connects compressor, indexer and attention for incremental CPU execution. It keeps per-source compressed KV and index keys and shares per-token selections and candidate masks across subsequent layers; block execution restores these states if MoE fails. A synthetic two-layer test checks partial and completed groups, reuse and rejection of out-of-order calls. This reference clones cache state for transactional updates and is not production-scalable. It has not been checked against checkpoint output.

`v41_model.rs` composes token embedding, Engram hashes and residual updates, all checkpoint-backed backbone blocks, and the output head into a text-only, single-sequence CPU reference. It rolls back sequence caches and hash state on a token error and can reset for a new sequence. A tiny synthetic one-layer checkpoint verifies multiple tokens, invalid-token handling and reset; this does not cover the pinned model's full topology, real weights, Engram or numerical agreement. Loading the real checkpoint and running full inference have not been demonstrated. This implementation copies caches for rollback and is unsuitable for production inference.

`v41_dspark.rs` adds CPU references for the DSpark target-hidden projection, anchor/noise token preparation, draft stages and final Markov-biased greedy draft and confidence heads. The backbone can return the configured target-layer residual means before attention. Draft attention seeds a main-token window and lets every draft position attend to the whole draft block; each stage uses the checkpoint's separate draft expert counts. A synthetic checkpoint exercises one complete draft stage and the draft-only runner, including failure rollback; a separate synthetic PyTorch vector matches the draft-head logits, greedy tokens and confidence values. Pinned shard-46 headers confirm the draft attention and head tensor shapes. The complete draft runner has not been numerically compared with the checkpoint reference or real weights. Non-greedy sampling, production generation, and GPU execution remain outstanding.

The CPU reference now optionally performs greedy target verification of DSpark drafts and falls back to the target token on rejection. The verifier advances the target one token at a time and maintains draft-cache alignment, so it is a correctness path, not a speculative speedup. Synthetic one-layer tests compare accepted and rejected draft cases, single-token prefill and EOS against ordinary target-only greedy output. `v41-reference --dspark` enables this path and reports checked and accepted draft counts; real-checkpoint and GPU verification remain untested. Non-greedy verification and production scheduling are not implemented.

The DSpark attention CPU path has now also been compared against a separate PyTorch formulation for a synthetic two-token draft block with a seeded main-token window; outputs agreed within 1%. The generator is `generate_v41_dspark_attention_vectors.py`. A synthetic three-stage checkpoint test checks accepted and rejected draft verification against ordinary greedy decoding. This does not establish full checkpoint equivalence or GPU execution.

`v41_vision.rs` adds CPU reference image-grid planning, image-placeholder expansion, token-type layout, normalized RGB patch ordering, checkpoint-backed BF16 aligner projections and image-span embedding assembly. Eight resize plans, patch values and token types were checked against the pinned `image_processor.py`; aligner unfolding and synthetic projection outputs were checked against PyTorch. The aligner was also evaluated with the pinned shard-1 weight range and synthetic 3×3 vision features: observed relative RMS error against PyTorch was 0.00000001. Fetch the 140 MiB range with `scripts/fetch_v41_reference_ranges.py --aligner <directory>` and set `SINGULARITY_V41_ALIGNER` for the ignored real-weight test. Image markers in that test are synthetic zeros. `patchify_rgb` expects pixels already decoded and resized/padded. Image decoding and resize, the vision encoder, multimodal model execution and serving remain unimplemented; this is not multimodal inference.

The CLI exposes this reference as `singularity v41-reference --model-path <checkpoint-directory> --config-path <config.json> --tokenizer-path <tokenizer.json> --request-path <request.json>`. A request can be `{"messages":[{"role":"user","content":"Hello"}],"mode":"chat","max_new_tokens":32}`; function tools and thinking mode are also accepted. It validates context length, builds the Engram tokenizer map, greedily generates, and returns token IDs, text and a parsed message if EOS is reached. It requires the complete checkpoint and is deliberately offline; only the command help and a tiny synthetic model's greedy path have been tested, not this command with real weights. The development server does not expose it.

The existing `TransformerModel` is a generic host implementation, not V4.1. The CUDA backend's existence does not make its forward pass execute on GPUs. The CLI therefore refuses `--use-cuda` and requires `--dev-mock` for the current development server. The API exposes `singularity-host-development` and rejects unavailable model IDs. This server is not a production deployment.

The CUDA backend now creates and manages driver streams and events rather than treating host timestamps as device events; it checks buffer bounds and GEMM shape/strides using the actual allocations, binds the CUDA context before transfers and GEMM, and returns unknown memory capacity on query failure rather than fabricating it. Explicit stream/event destruction is available, with remaining handles cleaned up when the backend drops. GEMM and synchronous copies still use the backend's default stream: the API does not yet dispatch operations onto the newly created streams, so their events must not be interpreted as timing or ordering GEMM work. `cargo check --workspace --features cuda` and CUDA-crate Clippy pass on the macOS host. An ignored physical-GPU transfer/GEMM/event test was added, but has not been executed on CUDA hardware. Modal CLI 1.4.3 is present; profile inspection did not complete in this environment and was cancelled. The local Docker daemon was unavailable. These observations do not establish Modal access, B200 availability, costs, or readiness to deploy.

`singularity-cuda/src/kernels/v41_quant.cu` and `CudaBackend::v41_quantized_matvec` add a correctness-first NVRTC-compiled CUDA path for BF16 input, block-FP8 activation quantization, native FP8 dense or FP4 expert weights, UE8M0 scales, and BF16 output. The implementation uses scalar CUDA threads, not optimized B200 tensor-core kernels, and synchronizes each call. Rust feature builds, buffer-layout tests, and a C++ host emulation smoke test pass; host emulation is not CUDA compilation. The ignored tests in `singularity-tests/tests/v41_cuda_quant.rs` compare synthetic matrices and actual expert-309 weights against the CPU reference on physical CUDA hardware. Neither NVRTC compilation nor GPU execution has been performed in this environment; the path is not yet connected to a V4.1 forward pass. Run on CUDA 13/SM100 with `cargo test -p singularity-tests --features cuda --test v41_cuda_quant -- --ignored`, setting `SINGULARITY_V41_EXPERT_WEIGHT` and `SINGULARITY_V41_EXPERT_SCALE` for the real-weight case.

Safetensors index metadata accepts numeric values and checks shard inventory and payload offsets; duplicate JSON keys in headers and indexes are rejected. The strict parser was verified against the pinned index (SHA-256 `74b0686a3d2891980d5e303251b075a3bccae2c2ff650747db2620a649b98fa8`, 96,085 tensors across 48 shards). Run `SINGULARITY_V41_INDEX=/path/to/model.safetensors.index.json cargo test -p singularity-model strict_index_parses_pinned_checkpoint_inventory -- --ignored`. It does not yet validate all dtype/shape rules, quantization metadata, or checkpoint-specific expected tensor names. Model loading, tokenizer protocol, V4.1 operators, distributed execution, production scheduling and serving, Modal infrastructure, physical GPU validation, and the DeepInfer comparison remain outstanding.

The workspace has Git metadata and uncommitted changes; consult `git status` for the current state. The local host is macOS; no B200 execution has been established.

The BF16 index scoring and the 64-position online sparse attention reference were compared to independent PyTorch 2.7.1 CPU formulations using synthetic vectors, including masked slots across two blocks. Both matched the stored vectors exactly; this does not establish CUDA kernel equivalence. The generators are `generate_v41_index_score_vectors.py` and `generate_v41_sparse_kernel_vectors.py`.
