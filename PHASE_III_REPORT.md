# SINGULARITY Phase III — current execution record

Status: **in progress; no V4.1 inference or deployment has been demonstrated**. The Phase II documents describe the earlier generic host transformer and do not establish Phase III capabilities.

## Checkpoint evidence

On 2026-10-30 the Hugging Face model API returned revision `1bae0e1088993b9b82de08f59de5be5a34e42170` for `deepseek-ai/DeepSeek-V4.1-Flash-1017`. The configuration fixture at `singularity-model/tests/fixtures/deepseek-v41-flash-1017-config.json` matches the configuration fetched by that immutable revision. Source: https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/tree/1bae0e1088993b9b82de08f59de5be5a34e42170 (MIT license). The index fetched at that revision has 96,085 entries, 48 distinct shard names and `metadata.total_size` 510,286,023,000 bytes. This is an index inspection only; no shard integrity or tensor shapes have been verified.

The config specifies 40 backbone layers, 3 draft layers, four residual streams, Engram layers 1 and 14, and a 32-layer vision encoder. Its quantization metadata specifies FP8, FP4 experts and UE8M0 scales. `v41_config.rs` parses a subset of the config and validates basic topology and quantization fields; it does not implement those operations. DeepInfer's `deepinfer/hugging_face/config.py` was consulted for the layer-source interpretation and quantization checks (Apache-2.0).

`singularity-model/src/engram.rs` implements a CPU reference for tokenizer compression, prime table layout and addressing, including sequence-start and image/dead-token boundaries. Its 1017 multipliers are fixed to the pinned config's 99,092-token compressed vocabulary and layer IDs. The test compares row totals and hash IDs with a separate NumPy/SymPy transcription of the checkpoint's MIT-licensed `inference/engram.py`; the vector generator is `singularity-model/tests/fixtures/engram_reference_vectors.py` (NumPy 2.5.4, SymPy 1.14.0). With the pinned tokenizer, the complete 129,280-entry compression map matched an independently generated Python tokenizers 0.21.4 SHA-256 digest; `engram_compression_reference.py` regenerates it. Run the external-asset test with `SINGULARITY_V41_TOKENIZER=/path/to/tokenizer.json cargo test -p singularity-model checkpoint_compressed_vocabulary_matches_reference -- --ignored`.

`v41_engram.rs` adds CPU row-wise FP8/UE8M0 embedding lookup, quantized projection, and the per-stream normalized residual gate. An entire miniature Engram forward matched a PyTorch CPU formulation. A component test also used four actual layer-14 embedding rows repeated across the 24 hash columns, the real 157,286,400-byte projection, scales and q/k weights, with a synthetic residual. It matched a separate PyTorch CPU formulation with relative RMS error 0.00000005. This is not real-prompt inference, a full checkpoint load, or GPU execution. `Flash1017HashState` now maps raw token IDs incrementally, keeps bounded history and resets per sequence; tests cover image boundaries, failure and reset. Distributed embedding placement and GPU execution remain unimplemented. The bounded shard-48 reference ranges and checksums are available through `scripts/fetch_v41_reference_ranges.py --engram-projection <directory>` (the flag additionally downloads approximately 150 MiB); the ignored full component test requires `SINGULARITY_ENGRAM_ROWS`, `SINGULARITY_ENGRAM_SCALES`, `SINGULARITY_ENGRAM_QK`, `SINGULARITY_ENGRAM_WKV` and `SINGULARITY_ENGRAM_WKV_SCALES`.

`v41_prompt.rs` implements the text-only system/user/assistant protocol in chat and thinking modes, including numeric effort, prior reasoning removal, and mid-conversation system messages. It deliberately rejects unsupported structured messages instead of discarding their fields. Seven vectors were generated with the pinned checkpoint's `encoding/encoding.py` and tokenizer; both serialized text and token IDs were compared. The generator is `singularity-model/tests/fixtures/generate_v41_text_vectors.py` and accepts paths to those pinned files. The token-ID test requires `SINGULARITY_V41_TOKENIZER=/path/to/tokenizer.json cargo test -p singularity-model text_token_ids_match_checkpoint_reference -- --ignored`. Tool calls, tool results, schema prompts, task tokens, images, output parsing, and integration into the serving path are still outstanding.

`v41_quant.rs` implements CPU reference decoding and matrix-vector operations for E4M3FN dense weights with 32×32 UE8M0 scales and E2M1FN packed experts with per-row, per-32 UE8M0 scales. A borrowed loader view checks dtype, shape and payload sizes without changing checkpoint bytes. The header of pinned shard 9 was retrieved by HTTP byte range: `layers.6.attn.wkv.weight` is `F8_E4M3 [512,5120]` with `F8_E8M0 [16,160]` scales, while `layers.6.ffn.experts.0.w1.weight` is `I8 [2304,2560]` with `F8_E8M0 [2304,160]` scales. Only the header was inspected, not the weight bytes. All 256 FP8 and scale byte values plus synthetic matrix vectors were compared with PyTorch 2.7.1 CPU; the generator is `singularity-model/tests/fixtures/generate_v41_quant_vectors.py`. These matvecs use unquantized FP32 inputs and are not the reference GPU kernel's quantized-activation GEMM; no actual checkpoint output or B200 numerical equivalence has been established.

`v41_hyper.rs` implements CPU Hyper-Connections coefficient projection, Sinkhorn normalization, pre/post transforms and shifted pre-mix state transitions, including optional BF16 activation boundaries. It loads the checkpoint's F32 HC tensors and validates their shapes. Synthetic vectors and two shifted steps were compared against an independent PyTorch CPU formulation. The layer-6 attention HC parameters were also retrieved from pinned shard 9 bytes 261472–2227659 (inclusive; SHA-256 `7c1dbec1f1e4f2e3e70dd6bcfc44304b8dd862a7753f5206fda2f7351cbc09bc`) and compared against PyTorch with a synthetic input. Regenerate vectors with `generate_v41_hyper_vectors.py` and run the real-weight test using `SINGULARITY_V41_HC_ATTN_BYTES=/path/to/range.bin cargo test -p singularity-model checkpoint_hyper_connection_matches_torch_reference -- --ignored`. This is not a full layer test; its input is synthetic, and the component is not yet integrated into a model forward pass or GPU backend.

`v41_sparse.rs` supplies CPU reference primitives for index scoring, candidate-block selection, causal compressed top-k, sliding-window indices and a single-sequence ring, per-coordinate compression pooling, and shared-KV attention with a learned sink. Synthetic attention, index and pooling values were compared against PyTorch CPU; prefill and incremental window results were checked across ring wraparound. Ties use deterministic ascending indices; compressed top-k pads when candidate filtering leaves too few valid positions, whereas the checkpoint reference may return masked positions at `-inf` in that edge case. The CPU attention computes ideal FP32 probabilities and does not reproduce the TileLang kernel's intermediate BF16 probability rounding. Projections, RoPE, quantization, cross-layer ownership, device cache, and full sparse attention execution are not yet connected.

`v41_rope.rs` implements CPU adjacent-pair RoPE and compressed-layer YaRN frequencies selected from checkpoint config; synthetic BF16 vectors at positions up to 1,048,575 were compared to PyTorch. `v41_quant.rs` now also encodes round-to-nearest-even E4M3FN activations with 32-element UE8M0 scales and provides a block-scaled CPU matrix path. The FP8 conversion's representable values and midpoints, plus activation block vectors, were checked against PyTorch. The real expert-309 test now additionally evaluates the quantized-activation path against a separate PyTorch dequantized formulation: observed relative RMS error 0 for that synthetic input. This does not establish TileLang or B200 equivalence; the CPU operations are not yet wired to a full V4.1 attention/model forward pass.

`v41_moe.rs` adds checkpoint-specific sqrt-softplus routing (bias affects selection only), text/image bias handling, routed and shared expert loading, clamped SwiGLU, and single-token local expert aggregation. Its CPU paths include both unquantized and block-quantized activation references; neither is an optimized GPU kernel. Synthetic packed experts and aggregation were compared to PyTorch CPU. The layer-6 BF16 gate weights (shard 9 bytes 4207672–8139831; SHA-256 `6e46b2f91b46aad3420f3dab6dedca03aebf94540f3819dd0c96f29aa5d0dc34`) and text/VL biases (bytes 258400–261471; SHA-256 `0a81d7f8e454f084206ee5db885e3963843ac452873187e4ccf3879055497d42`) were compared with PyTorch for a synthetic input. The selected expert 309 was then loaded from real checkpoint bytes (weights bytes 4735551032–4753245751; scales bytes 267059000–268164919) and evaluated using the gate's route weight. Its 5,120 BF16 outputs matched the corresponding PyTorch CPU calculation in this test (observed relative RMS error 0; tolerance 0.01). Both calculations use synthetic inputs and unquantized activation matvecs. The test constructs a small Safetensors subset and exercises the gate and expert loaders, not the complete distributed checkpoint loader. `scripts/fetch_v41_reference_ranges.py` retrieves these bounded ranges and verifies SHA-256 before storing them; its HTTP rejection paths were tested with mocked responses, while direct Python network access was denied in this environment. The ignored `routed_real_expert_matches_torch_reference` test takes `SINGULARITY_V41_GATE_WEIGHT`, `SINGULARITY_V41_GATE_BIAS`, `SINGULARITY_V41_EXPERT_WEIGHT` and `SINGULARITY_V41_EXPERT_SCALE`. The older generic `MoERouter` has different scoring semantics and is not a V4.1 router. Expert parallelism, GPU execution and full model execution remain unverified.

## Execution boundary

The existing `TransformerModel` is a generic host implementation, not V4.1. The CUDA backend's existence does not make its forward pass execute on GPUs. The CLI therefore refuses `--use-cuda` and requires `--dev-mock` for the current development server. The API exposes `singularity-host-development` and rejects unavailable model IDs. This server is not a production deployment.

The CUDA backend now creates and manages driver streams and events rather than treating host timestamps as device events; it checks buffer bounds and GEMM shape/strides using the actual allocations, binds the CUDA context before transfers and GEMM, and returns unknown memory capacity on query failure rather than fabricating it. Explicit stream/event destruction is available, with remaining handles cleaned up when the backend drops. GEMM and synchronous copies still use the backend's default stream: the API does not yet dispatch operations onto the newly created streams, so their events must not be interpreted as timing or ordering GEMM work. `cargo check --workspace --features cuda` and CUDA-crate Clippy pass on the macOS host. An ignored physical-GPU transfer/GEMM/event test was added, but has not been executed on CUDA hardware. Modal CLI 1.4.3 is present; profile inspection did not complete in this environment and was cancelled. The local Docker daemon was unavailable. These observations do not establish Modal access, B200 availability, costs, or readiness to deploy.

`singularity-cuda/src/kernels/v41_quant.cu` and `CudaBackend::v41_quantized_matvec` add a correctness-first NVRTC-compiled CUDA path for BF16 input, block-FP8 activation quantization, native FP8 dense or FP4 expert weights, UE8M0 scales, and BF16 output. The implementation uses scalar CUDA threads, not optimized B200 tensor-core kernels, and synchronizes each call. Rust feature builds, buffer-layout tests, and a C++ host emulation smoke test pass; host emulation is not CUDA compilation. The ignored tests in `singularity-tests/tests/v41_cuda_quant.rs` compare synthetic matrices and actual expert-309 weights against the CPU reference on physical CUDA hardware. Neither NVRTC compilation nor GPU execution has been performed in this environment; the path is not yet connected to a V4.1 forward pass. Run on CUDA 13/SM100 with `cargo test -p singularity-tests --features cuda --test v41_cuda_quant -- --ignored`, setting `SINGULARITY_V41_EXPERT_WEIGHT` and `SINGULARITY_V41_EXPERT_SCALE` for the real-weight case.

Safetensors index metadata now accepts numeric values and checks shard inventory and payload offsets. It does not yet validate all dtype/shape rules, quantization metadata, or checkpoint-specific expected tensor names. Model loading, tokenizer protocol, V4.1 operators, distributed execution, production scheduling and serving, Modal infrastructure, physical GPU validation, and the DeepInfer comparison remain outstanding.

The workspace has no Git repository metadata, so no source revision or working-tree diff can be recorded. The local host is macOS; no B200 execution has been established.
